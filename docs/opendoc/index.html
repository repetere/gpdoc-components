for documents.

Start with a small, inspectable document service. Build toward an experience you can host, extend, and make your own.

OpenDoc is an original MIT-licensed foundation: a local reference API, PostgreSQL storage, strict access-token validation, signed deployment profiles, experimental Yjs collaboration, browser sign-in, shared authentication state, and separate REST and live text editors.

01 / PROJECT STATUS

A working start.
A visible boundary.

Small enough to understand. Explicit about what is here and what still needs to be built.

AVAILABLE IN V0.8●

Local and adapter foundation

  • Authenticated local document API with tenant and role checks.
  • Revision conflict handling for guarded document updates.
  • Signed deployment-profile verification.
  • Conformance tests and cloud-neutral interfaces.
  • PostgreSQL storage with transactional revision checks.
  • Pinned-key RS256 access-token validation and server-owned membership.
  • Experimental authenticated WebSocket/Yjs rooms with durable PostgreSQL snapshots.
  • Browser OIDC login, protected sessions, and server-owned account mapping.
  • Optional encrypted PostgreSQL state for shared browser authentication.
  • Authenticated REST text editing with explicit saves and revision-conflict review.
  • Opt-in live text collaboration with a separate Yjs authority and persisted update acknowledgements.
  • Automatic live-ticket renewal and bounded reconnect with visible pending-work status.
  • Opt-in cross-instance live synchronization through one shared PostgreSQL primary.
  • Node.js 22+ with pinned adapter dependencies.

Demo authentication uses a local temporary token. It is not enterprise OIDC login. Browser-login tests use a synthetic provider. Sessions default to memory, with an optional PostgreSQL adapter. The opt-in live editor uses a separate Yjs document authority with durable update acknowledgements; REST documents keep their revision-based saves. Pending live edits remain only in the open tab until confirmed; automatic reconnect is not a durable offline queue. Cross-instance synchronization requires explicit configuration against the same PostgreSQL primary and schema; database failover and multi-primary safety are not provided. Both modes remain experimental. These adapters do not upgrade the default memory demo.

PLANNED / NOT IMPLEMENTED○

The production path

  • Production identity-provider validation, collaboration scaling, and rich-text editor integration.
  • Durable browser offline recovery with explicit retention and account isolation.
  • Production database operations and S3 / GCS / Blob storage adapters.
  • Cloud infrastructure as code and tested deployment recipes.
  • Configurable branding and rebrandable VS Code clients.
  • Verified air-gap operation and production hardening.

These are roadmap goals, not release promises. No cloud deployment is claimed or verified here.

02 / GET STARTED

From source
to localhost.

You need Git and Node.js 22 or newer. Clone the public repository, run the checks, then start the local demo.

No cloud account is needed. Install the pinned packages for adapter tests; the memory demo itself uses only Node built-ins. Read the source before running it.

Read the source and setup notes →

To try sign-in and editing, use the separate synthetic local editor guide. It starts a loopback-only test identity provider and an ephemeral workspace. The separate live editor guide covers collaborative editing and its limits. This page is not a hosted document service.

TERMINAL / LOCAL REFERENCE
git clone https://github.com/repetere/gpdoc-components.git
cd gpdoc-components/opendoc
npm ci --ignore-scripts
npm test
npm run demo
↳ Starts on loopback · follow the terminal output

For local exploration only. The demo binds to loopback and uses a temporary authentication fixture. Documents are stored in memory and disappear when the process stops. Do not expose it to the internet or treat it as a production identity or storage service.
03 / ARCHITECTURE

Keep the contract.
Change the infrastructure.

The core defines document operations and their boundaries. Production identity, persistence, and collaboration belong behind explicit interfaces.

  1. 01

    Authenticate, then authorize

    Tenant and role checks belong at the service boundary. The default demo uses a temporary token. The optional validator checks signed access tokens against pinned keys; the separate browser-login adapter uses authorization code and PKCE. Production provider validation remains planned.

    IDENTITY
  2. 02

    Make revisions explicit

    A stale revision must produce a conflict rather than silently replace newer content. REST documents use conditional replacement. Live documents use Yjs updates and reject snapshot replacement. The two collections stay separate, with no automatic conversion or dual writing.

    DOCUMENTS
  3. 03

    Verify the deployment profile

    Check signed profile data before relying on its configuration. Signature verification is one building block, not proof of a secure or successful deployment.

    CONFIGURATION
  4. 04

    Connect production services

    The PostgreSQL adapter now provides transactional document storage. Cloud object stores, hosted deployment and production operations still require implementation and validation.

    ADAPTERS

Read the architecture and API contract, the deployment-profile trust model, PostgreSQL setup, authentication boundaries, the experimental collaboration protocol, browser-login setup, shared sessions, the REST web editor, or the opt-in live editor.

Working with the files themselves? The existing GPDoc Markdown reference covers portable document identity and review metadata. OpenDoc adds a separate service foundation.
